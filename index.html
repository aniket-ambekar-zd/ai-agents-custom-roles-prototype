AI agent access

Least privilege by default Every control in this section defaults to its most restrictive option. A new role grants nothing until an admin deliberately opens each capability. This is a change from the drafted API1 requirement, which defaulted API integrations to View Only.

Default changed — and it changes the PRD API1 currently specifies two options with View Only as the default. Least privilege makes No access the correct default, which means a third option and a third scope. Worth confirming: is "cannot see integrations exist" a distinct scope from "can see the list", or is hiding the area a UI decision on top of a denied read?

Open design question One control here covers five separate entity types. A customer who wants “manage templates but not intents” is blocked by this grouping, not by the platform. Splitting it later is a UI change, not a permissions change.

Ownership and scope Subsequent

Restrict which AI agents this role can manage. Applies to every capability selected above.
“Manage selected AI agents” replaces an internal-only capability Restricting a customer admin to specific AI agents exists today, but only the internal Zendesk Admin role can configure it — which means a customer cannot self-serve it, and it cannot be handed to the customer admin directly without letting them lift their own restriction. Moving it here fixes that: the configurer becomes the account's Support admin or owner, a higher authority than the role being restricted. The dashboard version is being removed under Admin Role Deprecation with a deliberate capability gap until this control ships.
No AI agents selected
An allowlist goes stale — decide what a new agent inherits This is a list of specific agent IDs, so an AI agent created after the role is configured belongs to no list and is invisible to this role until an admin edits it back in. That is the correct least-privilege default, but it is a real operational cost and it is silent — the admin who creates the agent is often not the admin who owns the role. Needs an explicit product decision: silent exclusion, a warning at agent creation, or an "include new agents" opt-in.
This one is an instance list, not an attribute condition Ownership and brand scoping compare an attribute on the resource (owner_id, brand_id). This compares the resource's own identity against a stored set, so the set has to live somewhere and be passed into the policy evaluation. Precedent: group ID is absent from the auth token and is passed explicitly in request_data. Confirm with Esa whether the permitted set is a policy-statement condition on the role or something the product supplies per request — the answer changes who stores it and who keeps it in sync.
One brand per role. To cover a user across two brands, create a second role — a team member can hold only one Support role at a time.
Single-select is a real constraint, not a simplification Because a user holds one Support role, one brand per role means brand-scoped users cannot span brands at all. Confirm this matches what the requesting customer actually needs before it becomes the shipped model — multi-select later is a schema change, not a UI change.
Brand scoping is blocked on an upstream gap — selected agents is not The enforcement mechanism exists for all of these — conditional scopes return filter expressions the product applies to its queries. What does not exist is brand as an attribute on an AI agent. Today brand selection at agent creation scopes the knowledge base only; it does not control access, so the brand option cannot ship until that changes.

Manage selected AI agents does not have that dependency — the AI agent is the resource itself, so there is no new attribute to expose. That makes it the cheapest of the three scoping options to enforce and the one most likely to fit a subsequent release.
First release stops here Analytics, Settings, Content, and Ownership and scope controls arrive in a subsequent release. Toggle + Subsequent in the banner to preview them.
Permission changes are not instant Live copy candidate: “Changes to AI agent permissions can take up to a minute to apply for signed-in users.” Raised because enforcement evaluates a cached policy bundle, not the database, at request time. Needs to become an explicit PRD requirement.

Roles and access

Team members can only have one Support role at a time.
ⓘ Defined by Support role — AI agent access for this user is managed by the custom role assigned above.
ADM5–ADM7 — and the reason it matters AI Agents has its own three product roles (admin, editor, user). When a custom role carries AI agent permissions, the custom role has to win, or two systems grant access to the same user and the compliance story collapses. Disabling this field is the visible half; the invisible half is our code ignoring the product role — which is the enforcement work most likely to be underestimated.
Unresolved What happens to a user who already has an AI agent product role when they are moved into a custom role that carries AI agent permissions? Migration behaviour for existing custom-role accounts is not yet decided. Question for the Aug 5 sync.
